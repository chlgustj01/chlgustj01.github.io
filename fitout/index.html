Background & Approach

표를 보여주는 게 아니라, 판단할 수 있게

처음엔 공정 전반을 다루는 시스템도 검토했지만, 제한된 기간 안에 데이터 연동을 끝까지 구현하기 위해 입고·보관·불출 흐름이 명확한 의장 자재관리로 범위를 좁혔습니다. 기획부터 화면 설계, 데이터 구조 정의, 구현, 테스트까지 개발은 직접 맡아 진행하되, 팀원들과 꾸준히 의견을 나누고 피드백을 반영하며 세 가지에 집중했습니다.

01 / 설계

업무 흐름 기반 데이터 구조

BOM·입고·창고·불출 Excel을 화면 단위가 아니라 실제 자재 흐름 기준으로 연결했습니다. 입고 완료 한 번이 검수상태·재고·Rack·확보율·KPI까지 연쇄적으로 바뀌도록 설계했습니다.

02 / 정합성

데이터 정합성 & 업무 로직

ClosedXML로 여러 시트를 조회·수정하며 자재 상태·확보율·지연 여부를 자동 판정했습니다. 헤더명 기준으로 열 위치를 찾는 공통 헬퍼를 만들어 Excel 열 순서 변경에도 코드가 깨지지 않게 했습니다.

03 / 시각화

GDI+ 기반 커스텀 차트

외부 차트 라이브러리 없이 Panel.Paint와 Graphics로 도넛 차트·추이 그래프·Rack Map을 직접 구현했습니다. 화면 크기가 변해도 폰트·두께·범례 간격이 함께 스케일링되도록 clamp 처리했습니다.

자재 데이터는 어떻게 마련했나

조선소 의장자재는 호선마다 치수·사양이 달라지는 오더메이드(주문제작) 구조재 비중이 커서, 실제 발주 데이터를 그대로 가져와 쓸 수 없었습니다. 그래서 호선이 바뀌어도 품목 자체는 반복적으로 쓰이는 소모성 의장자재 위주로 조사해 자재번호·규격·안전재고 기준을 담은 자체 DB를 구성하고, 이 데이터를 기준으로 프로그램을 구현했습니다.

Screens

4개 화면, 하나의 자재 흐름

각 화면은 독립된 표가 아니라 입고 → 보관 → 불출이라는 실제 업무 흐름으로 연결되어 있습니다. 한 화면에서의 처리가 다른 화면에 자동으로 반영됩니다.

01 / Dashboard

종합 대시보드

입고·창고·불출에서 발생한 데이터를 실시간으로 집계해 KPI, 자재 상태 도넛 차트, 최근 7일 입·불출 추이, 품목별 재고 현황을 한 화면에서 보여줍니다. 직접 업무를 처리하는 화면이 아니라, 세 화면의 데이터를 모아 위험 요인을 판단하는 모니터링 화면입니다.

System Flow

입고 확인 버튼 클릭, 그 다음

자재 입고를 확인 처리하면 아래 여섯 단계가 한 번에 연쇄적으로 갱신됩니다. 화면을 각각 만들지 않고 이 흐름을 먼저 정의한 뒤 화면을 붙였습니다.

왜 체인으로 설계했는가

  • 단일 진입점 — 입고 확인 버튼 하나가 모든 연계 갱신의 트리거입니다. 화면마다 따로 처리하면 불일치가 생깁니다.
  • 중복 처리 차단 — 처리 직전 Excel 원본 상태를 재확인해, 이미 입고완료인 자재는 재처리를 막습니다.
  • 즉시 반영 — 창고·대시보드 화면을 열어두고 있어도 같은 흐름 안에서 수치가 함께 바뀝니다.
  • 신규 자재 예외 — 기존 Rack 정보가 없는 신규 자재는 자재 Master → 권장창고 → 빈 Rack 탐색 순으로 위치를 자동 배정합니다.
Problem Solving

개발 중 부딪힌 6가지 문제

보기 좋은 화면보다 먼저, 숫자를 믿을 수 있는지를 검증해야 했습니다. 가장 크게 시간을 쓴 여섯 가지 문제와 해결 방식입니다.

CASE 01

KPI 중복 집계

문제한 자재가 입고지연·불출지연·안전재고부족에 동시에 해당되면서 KPI 합계가 실제 관리 대상 수와 맞지 않았습니다.
해결입고지연 → 불출지연 → 안전재고부족 → 기타 → 정상 순으로 5단계 우선순위를 정의하고, 자재당 대표 상태를 하나만 부여했습니다.
결과KPI 합계와 실제 관리 대상 수가 일치해 데이터 정합성을 확보했습니다.
CASE 02

평균이 가리는 위험 Rack

문제Rack 전체 재고량이나 평균 확보율을 쓰면 과잉 품목(A 200%) 때문에 부족 품목(B 20%)이 평균 110%의 정상처럼 보였습니다.
해결평균이 아니라 Rack 내부에서 가장 위험한 품목을 Rack의 대표 상태로 판정하도록 바꿨습니다.
결과창고 배치도에서 실제 작업에 영향을 줄 수 있는 부족 Rack을 즉시 찾을 수 있게 됐습니다.
CASE 03

화면 간 단절

문제입고 상태만 바꾸면 창고 재고·Rack·확보율이 실제 업무 상태와 어긋났습니다.
해결입고 처리 한 번으로 입고일·검수상태·재고수량·Rack 위치·확보율·재고상태가 연쇄적으로 갱신되도록 설계했습니다.
결과4개 화면이 독립된 표가 아니라 하나의 업무 시스템처럼 연결됐습니다.
CASE 04

신규 자재의 보관 위치

문제신규 자재는 기존 Rack 정보가 없어 입고 후 어디에 보관할지 결정할 수 없었습니다.
해결기존/신규 자재를 구분하고, 신규 자재는 자재 Master → 권장창고 → 빈 Rack 탐색 → 자동 위치배정 순으로 처리했습니다.
결과입고부터 보관 위치 결정까지의 흐름을 자동화했습니다.
CASE 05

중복 처리로 인한 데이터 오염

문제같은 자재를 두 번 입고 처리하면 재고가 중복으로 증가할 가능성이 있었습니다.
해결처리 직전 Excel 원본 상태를 다시 확인해, 이미 입고완료인 자재는 재처리를 차단했습니다.
결과사용자 오조작에 의한 중복 처리와 재고 데이터 오염을 방지했습니다.
CASE 06

끊임없는 요구사항 변경

문제안전재고 기준, KPI 정의, 불출 상세조건 같은 세부 기준이 개발 중 계속 바뀌었습니다.
해결Notion에 변경사항·우선순위·완료 여부를 기록하고, 코드도 Dashboard/Data/Charts/Search 등 Partial Class로 분리했습니다.
결과요구사항이 바뀔 때마다 관련 기능만 빠르게 찾아 수정할 수 있었습니다.
Design Criteria

안전재고 기준은 왜 125% 인가

창고 화면의 모든 색(정상/안전마진 부족/소요량 부족) 판정은 이 하나의 기준에서 출발합니다.

목표재고 = 기준 수량 × 125%

한 호선 작업에 필요한 기준 수량에 25%의 예비분을 더해 목표재고로 설정했습니다. 확보율이 100% 미만이면 소요량이 부족한 상태, 100~125%는 작업은 가능하지만 안전마진이 부족한 상태, 125% 이상이어야 정상으로 판정합니다.

확보율 = 현재재고 ÷ 기준수량(100%) × 100
What I Learned

데이터로 배운 네 가지

01

UI보다 업무 흐름을 먼저 설계해야 한다

어떤 데이터가 언제 바뀌고 다른 데이터에 어떻게 영향을 미치는지를 먼저 정의하는 것이, 화면을 어떻게 구성할지보다 훨씬 중요했습니다.

02

시각화의 핵심은 신뢰할 수 있는 기준이다

차트를 보기 좋게 만드는 것보다, KPI가 중복 집계되지 않는지, 평균값이 위험을 가리고 있지는 않은지를 검증하는 게 우선이었습니다.

03

평균보다 Worst Case가 중요한 상황이 있다

Rack 재고처럼 품목 하나의 부족만으로도 작업에 영향을 줄 수 있는 경우엔, 가장 위험한 상태를 보여주는 방식이 실제 의사결정에 더 적합했습니다.

04

데이터 변경에는 추적성이 필요하다

결과만 보여주는 것보다, 누가 무엇을 바꿨고 어떤 값이 바뀌었는지 기록할 수 있는 구조가 업무 시스템에서는 중요하다는 걸 체감했습니다.
